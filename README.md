# IoT-Based Solar Panel Monitoring System
### with an anomaly-detection experiment for predictive-maintenance research

An end-to-end system for collecting, validating, logging, and analyzing
real-time solar panel performance data using Arduino-based hardware, extended
with a small, reproducible machine-learning study: **can operating measurements
reveal unusual operating conditions that warrant investigation?**

![Performance chart](analysis/output/performance_summary.png)
*Sample output from `analyze_performance.py` on a simulated 12-hour daylight
cycle (see `data/sample/`).*

> **Read this first — what is and is not real.**
> The repository's sample dataset is **simulated** (one fault-free day, no labels).
> The ML benchmark below uses a **simulated multi-day dataset with injected,
> labelled faults** (`research/simulate.py`). No result in this repository comes
> from hardware measurements, and none of the "faults" are real equipment
> failures. The benchmark measures how well each method finds the *specific
> deviations I injected*; it is a methods exercise, not evidence about real panels.

## 1. Project overview

The original project (unchanged) covers data acquisition and quality control:
Arduino sensing, on-device and host-side validation, CSV logging, and a
descriptive performance analysis (peak/average power, energy yield).

The `research/` extension adds the analytical layer the original lacked.
Before this work the repository contained **no machine learning**, and the only
"anomaly detection" was fixed range checking.

## 2. Problem statement, objectives and research question

**Problem.** Fixed range checks catch impossible readings (e.g. 30 V from a 24 V
panel) but not readings that are *plausible in isolation and wrong in context*:
a 1.1 A current is normal at dawn and a warning sign at noon.

**Research question.** *Given simultaneous light, temperature and electrical
measurements, can a model of expected behaviour (or a generic unsupervised
detector) identify unusual operating conditions that fixed range checks miss?*

**Objectives.**
1. Audit the existing system and its data (Section 3, 5).
2. Assess data quality and relationships between operating conditions and outputs.
3. Benchmark a baseline against two kinds of detector using a leakage-safe,
   chronological protocol.
4. Interpret results, including failure modes, and state what they do *not* show.

**Terminology used consistently.**

| Term | Meaning here | Done in this project? |
|---|---|---|
| Monitoring | Observing/logging measurements | Yes (original system) |
| Anomaly detection | Flagging observations that differ from expected patterns | **Yes — the task studied** |
| Fault classification | Assigning known fault labels | No (no real labelled faults exist) |
| Failure prediction | Estimating future failures | No (no run-to-failure data) |

Only anomaly detection is supported by the available data. A flagged point means
"worth a look", never "confirmed fault".

## 3. Existing IoT system architecture

```
 Solar panel ─┬─ voltage divider ──► A0 ┐
              └─ ACS712 current ───► A1 │  Arduino Uno/Nano
 LDR + resistor ───────────────────► A2 ├─ firmware/solar_monitor.ino
 DHT22 (temp, humidity) ───────────► D2 ┘   • reads every 2 s
                                            • computes power = V × I
                                            • status: OK / SENSOR_FAULT / OUT_OF_RANGE
                                  serial CSV, 9600 baud
                                            ▼
                      data_logger/logger.py  (host)
                      • schema check, range check
                      • accepted rows → solar_readings_<ts>.csv
                      • rejected rows + reason → solar_rejects_<ts>.csv
                                            ▼
              analysis/analyze_performance.py   (descriptive: power, energy, plots)
              research/                          (NEW: anomaly-detection experiment)
```

Measurements per row: `voltage_v, current_a, power_w, temp_c, humidity_pct,
light_pct, status` (+ host-side `timestamp_utc`). Note that `temp_c` is *ambient*
temperature (DHT22), not panel temperature, and that `timestamp_utc` is the host's
receive time. Audit notes on the original code are in `docs/methodology.md`.

## 4. Dataset

| Dataset | Source | Role |
|---|---|---|
| `data/sample/solar_readings_sample.csv` | Original repo; **simulated** | Data-quality check; clean-day sanity check |
| Generated by `research/simulate.py` | **Simulated**, calibrated to the sample file by least squares; 14 days × 360 rows (2-min interval) per seed | Training / validation / test |

Test days contain 4 injected fault episodes each (labelled in `is_anomaly`,
`fault_type`, `event_id`; every row carries `data_source=SIMULATED`):

| Fault type | What is injected | Real-world analogue (illustrative) |
|---|---|---|
| `current_drop` | current × 0.55–0.80 for 20–48 min | partial shading / soiling |
| `stuck_current` | current frozen at last value, 16–32 min | frozen/failed sensor |
| `voltage_spike` | +3–5 V for 1–3 samples, still inside valid range | transient / loose connection |
| `range_violation` | 25–30 V for 1–2 samples | outside valid range (existing logger would *reject* it) |

About 9 % of test rows are anomalous — **far higher than real prevalence**, chosen
so each fault type has enough examples to measure. Fault patterns are my design
and the benchmark rewards models that match them.

**Recommended real public dataset for follow-up:** *Solar Power Generation Data*
(two photovoltaic plants in India, 34 days, ~15-minute sampling, inverter-level
DC/AC power plus plant-level irradiation and temperature; Kaggle, by Ani Kannal;
also described on IEEE DataPort). It has no ground-truth fault labels, so it would
support unsupervised anomaly detection and expected-power modelling, not fault
classification. I could not download it in this environment, so **it has not been
used here**.

## 5. Data preparation (`research/data_prep.py`)

1. **Schema validation on load** — missing columns/timestamps raise clear errors.
2. **Quality report** — missing values, duplicate rows/timestamps, `-999` sentinels,
   out-of-range counts, sampling gaps, and `|power − V×I|` consistency.
3. **Findings on the repo sample** (`research/results/data_quality_repo_sample.json`):
   360 rows, no missing/duplicate/out-of-range values, regular 2-min sampling,
   power consistent with V×I to 0.005 W, all `status=OK`. Clean — but also
   *too* clean: voltage, current, temperature and light correlate at 0.99–1.00,
   which real hardware would not produce. This is a signature of simulation and
   is why no real-world claims are made.
4. **Features** — raw: voltage, current, power, temperature, humidity, light.
   Engineered (Isolation Forest variant only): `current_per_light` (current
   normalised by sunlight) and `current_roll_std` (std of the last 5 readings,
   same day, causal).
5. **Chronological split by whole days**: days 1–8 train (clean), 9–10
   validation (clean, used only to set alert thresholds), 11–14 test (faults).
   Whole days are used because adjacent 2-minute samples are near-duplicates; a
   random row split would leak.

## 6. Methods (`research/detectors.py`)

| Method | Idea | Trained on |
|---|---|---|
| **Range thresholds** (baseline) | Flag any reading outside the logger's valid ranges (imports `VALID_RANGES` from `data_logger/logger.py`) | nothing |
| **Expected-behaviour residual** | Quadratic regression predicts voltage and current from light + temperature; flag large standardised residuals (robust MAD sigma) | clean training days |
| **Isolation Forest (raw)** | Unsupervised outlier detector on the six raw features | clean training days |
| **Isolation Forest (+ engineered)** | Same, plus the two engineered features | clean training days |

Score-based methods share one threshold rule: the 99th percentile of scores on
clean validation data (≈1 % false-alarm budget). No labels are used for tuning.

## 7. Training and testing procedure

`python -m research.run_experiment` repeats the whole pipeline for **10
simulation seeds** (different weather, noise, and fault timing): simulate →
split chronologically → fit on train → calibrate threshold on validation →
evaluate once on test. Reported values are mean ± standard deviation across
seeds. Running it twice gives byte-identical `per_seed_results.csv`.

## 8. Evaluation metrics

- **Precision / recall / F1** (row level) and confusion matrices — the standard
  trade-off between false alarms and missed anomalies.
- **Event recall** — share of fault *episodes* with ≥1 flagged row; closer to what
  an operator cares about.
- **False alarms per day** — practical alert burden (360 rows/day).
- **ROC-AUC / PR-AUC** — threshold-free ranking quality (score-based methods
  only). PR-AUC is emphasised because anomalies are rare; the no-skill PR-AUC
  equals the prevalence (~0.09).
- **Recall by fault type** — shows *which* problems each method sees.

Because the labels are injected, these metrics are valid **for this synthetic
benchmark only**. On real data without fault labels, such numbers could not be
computed and evaluation would need domain review of flagged periods.

## 10. Discussion and limitations

**What the results show (on this synthetic benchmark).**
- Fixed range checks have perfect precision but find only the one fault type that
  leaves the valid range (recall 0.05, event recall 0.25). Most injected faults
  are invisible to them because each reading is individually plausible.
- A model of *expected behaviour given conditions* detected most episodes
  (event recall 0.87) and almost all current drops and voltage spikes.
- Isolation Forest performed poorly here. A targeted probe showed its score
  saturates at roughly the training maximum — a 30 V reading scored no higher than
  19.3 V — because its random splits are drawn from the training range and it
  cannot extrapolate beyond it. The engineered `current_roll_std` feature is
  exactly 0 during stuck episodes (never seen in training), yet recall stayed
  low, which is consistent with the same limitation. Its false-alarm rate also
  varied widely across seeds (sd 9.8/day), reflecting sensitivity to weather
  differences between validation and test days.
- The residual model's weak spot is `stuck_current` (recall 0.27): a frozen value
  looks fine until it drifts away from what conditions predict (visible in
  `fig2`). A rolling-variance rule would target this directly.

**What they do not show.**
- That any method works on real panels. Faults are injected by me; the
  residual model learns the same kind of light→current relationship the simulator
  used, so its advantage is partly **by construction**.
- That a flagged point is a fault. It only marks a departure from learned normal.
- Anything about predicting failures or classifying fault causes.

**Other limitations.** Daylight-only data; no seasonal/long-term effects; the
simulated light–voltage relationship is far tighter than real hardware; at a
1 % false-alarm budget the best method still raises ~3 false alarms/day at 2-min
sampling, which is too noisy for real alerting without persistence rules
(`fpr_sensitivity.csv` shows the trade-off). Sanity check: on the repo's clean
sample day the detectors flag 0–0.3 % of rows, as expected — but the simulator
was calibrated on that file, so this is not an independent validation.

**What would be needed next.** Real logged data from the rig across weeks and
seasons; a physically grounded expected-power model (irradiance, panel
temperature); labelled or maintenance-confirmed events; evaluation with
persistence/alert rules.

## 11. Installation and execution

```bash
pip install -r requirements.txt        # Python 3.10+ recommended
python -m research.run_experiment      # from the repo root; roughly 30 s; writes research/results/
python -m research.run_experiment --seeds 3 --outdir /tmp/results   # quicker run
python -m unittest discover tests      # or: pytest tests/ -v
```

Using real logs (no labels): `load_readings()` accepts the logger's CSV;
`quality_report()` and the detectors' `score()` work without labels, but
accuracy metrics cannot be computed.

Versions used for the committed results are in `research/results/run_metadata.json`.

## Getting started

### 1. Flash the firmware

Open `firmware/solar_monitor.ino` in the Arduino IDE, select your board, and
upload. It streams CSV data over serial at 9600 baud every 2 seconds.

### 2. Set up the Python environment

```bash
pip install -r requirements.txt
```

### 3. Log data from the device

```bash
cd data_logger
python logger.py --port /dev/ttyUSB0 --baud 9600 --outdir ../data
# Windows: --port COM3
```

This writes `solar_readings_<timestamp>.csv` (accepted rows) and
`solar_rejects_<timestamp>.csv` (flagged rows with reasons) to `../data`.

### 4. Analyze performance

No hardware? Try it on the included sample dataset:

```bash
cd analysis
python analyze_performance.py --input ../data/sample/solar_readings_sample.csv --outdir ./output
```

This prints a summary (peak power, average power, estimated energy yield,
average environmental conditions) and saves a three-panel trend chart to
`./output/performance_summary.png`.

### 5. Run the tests

```bash
pytest tests/ -v
```

`tests/test_logger.py` (15 tests) covers the validation logic end to end — schema checks, range
checks, firmware-fault passthrough, and logging/summary behavior — without
needing any hardware connected. `tests/test_research.py` (23 tests) covers the
data preparation, simulation, detectors and evaluation metrics.

## Current limitations

- Single-panel only; no multiplexing for multiple panels on one Arduino.
- No on-device buffering (e.g. SD card) — if the host disconnects, samples
  during that window are lost rather than queued.
- Longest continuous field test to date is a single daylight cycle, not a
  multi-day soak test.

## Conclusion and future work

Conclusion: on simulated data with injected faults, a model of expected behaviour
given conditions clearly outperformed both fixed range checks and Isolation Forest,
but this is a methods demonstration whose advantage is partly built into the
setup, not evidence of performance on real equipment.

Research future work: collect real multi-week rig data; add a rolling-variance
rule for stuck sensors; test a physically grounded expected-power model; evaluate
persistence-based alerting; try the public inverter-level dataset above.

Engineering future work (original list):

- Add SD card buffering on the Arduino side for host-disconnect resilience.
- Support multiple panels via analog multiplexer (e.g. CD74HC4067).
- Add a lightweight web dashboard for live monitoring instead of CSV-only
  output.
- MQTT publishing option for integration with a broader IoT stack.
